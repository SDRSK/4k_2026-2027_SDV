# Практична робота №3. Концептуальна ER-модель у CASE-засобі

**Предметна область:** бібліотека коледжу.  
**CASE-засіб:** diagrams.net (Draw.io); файл `Концептуальна_модель.drawio`.  
**Експорт:** `Концептуальна_модель.png` та `Концептуальна_модель.svg`.

## 1. Межі системи

Система підтримує облік книг, авторів, примірників, читачів і працівників, створення та закриття видач і пошук прострочень. Система повинна відповідати на питання: «Які книги є в каталозі?», «Хто автор книги?», «Які примірники має видання?», «У кого зараз конкретний примірник?», «Які видачі прострочені?», «Хто оформив видачу?». За межами системи — закупівлі, оплата штрафів, облік фінансів і міжбібліотечний обмін.

## 2. Побудована модель

Виділено сім сутностей: Книга, Автор, КнигаАвтор, Примірник, Читач, Бібліотекар, Видача. Первинні ідентифікатори: `book_id`, `author_id`, (`book_id`, `author_id`), `copy_id`, `reader_id`, `librarian_id`, `loan_id`. Кожна видача посилається рівно на одного читача, бібліотекаря й примірник. Історія видач не перезаписується під час повторної видачі. M:N між книгою та автором розв'язано проміжною сутністю `BookAuthor`. Повні атрибути та домени наведено у звіті ПР №2.

## 3. Перевірка сценаріями

| Сценарій | Перевірка моделі | Результат |
|---|---|---|
| Додати нову книгу без авторів і примірників | `Book` не потребує дочірнього запису | Підтримується; 0..N з обох залежних від книги зв'язків |
| Зареєструвати нового автора без книг | Для `Author` немає обов'язкових зворотних посилань | Підтримується |
| Додати примірник | Створити `Copy` з наявним `book_id` | Підтримується; FK обов'язковий |
| Змінити назву книги | Оновлюється лише `Book.title` | Підтримується; видачі не дублюють назву |
| Оформити видачу | `Loan` має існуючі `copy_id`, `reader_id`, `librarian_id` | Підтримується; перевірка доступності потребує додаткового правила |
| Повернути примірник | Встановити `Loan.returned_at` | Підтримується; збережено історію |
| Видалити книгу з примірниками | Посилання не дозволяють зруйнувати історію | Пряме видалення заборонено (RESTRICT); спочатку вирішити долю примірників |
| Видалити автора, що має книги | Каскадне очищення лише зв'язків `BookAuthor` | Підтримується, книги залишаються |
| Перехідний стан: книгу ще не комплектували | Книга існує з 0 примірниками | Підтримується |
| Перехідний стан: видачу оформлено, але книгу ще не повернуто | `returned_at = NULL` | Підтримується |
| Одночасно дві відкриті видачі одного примірника | Частковий унікальний індекс на `Loan.copy_id WHERE returned_at IS NULL` | Підтримується на логічному/фізичному рівні, не лише концептуальними кардинальностями |

## 4. Зафіксовані припущення

1. Кожний фізичний примірник належить рівно одному виданню, але видання може не мати примірників.
2. Одному ISBN відповідає одне бібліографічне видання; ISBN може бути відсутнім.
3. Читач і автор можуть бути зареєстровані без видач та співавторств.
4. Дату повернення зберігаємо як необов'язкову, окремий статус «видано» не дублюємо.
5. Один примірник може мати лише одну незакриту видачу; історичні видачі дозволені.
6. Видалення книги з примірниками, примірника з історією або читача з видачами заборонено задля аудиту.
7. Поле `condition` описує фізичний стан примірника (`available`, `repair`, `lost`), а не факт поточної видачі.

## 5. Відкриті питання до власника вимог

- Чи дозволена видача примірника зі станом `repair` або `lost`? **Попереднє рішення:** ні, застосунок перевіряє стан.
- Чи треба зберігати історію змін ПІБ читача? **Попереднє рішення:** ні, окремий аудит не реалізовано.
- Чи потрібні резервування/черги очікування? **Попереднє рішення:** поза межами цієї моделі.
- Чи потрібна підтримка кількох екземплярів одного ISBN із різними перевиданнями? **Попереднє рішення:** різні видання мають різні бібліографічні записи.
- Чи потрібні продовження строку та штрафи? **Попереднє рішення:** у поточній версії не передбачено.

## 6. Висновок

Концептуальна модель охоплює всі обрані бізнес-об'єкти, їхні ідентифікатори та суттєві зв'язки. Сценарії створення, оновлення, повернення і проміжних станів підтримуються. Правила обов'язкової участі не заважають попередньому внесенню даних до каталогу. Зв'язок M:N нормалізовано через проміжну сутність. Деякі динамічні умови, зокрема заборона паралельних відкритих видач, необхідно реалізувати додатковими обмеженнями на наступному етапі. **Модель готова до перетворення на реляційну схему** з урахуванням указаних припущень.

## Відповіді на питання для захисту

1. Створити тестовий об'єкт без дочірніх записів і перевірити, що мінімальна кардинальність для відповідного зв'язку дорівнює 0; у реляційній схемі перевірити відсутність FK у батьківській таблиці, що вимагає дочірнього рядка.
2. Припущення документують невизначені бізнес-правила й дозволяють власнику вимог їх підтвердити, не маскуючи їх як перевірені факти на діаграмі.
3. Концептуальна ER-модель описує предметні сутності та правила бізнесу незалежно від СКБД; логічна модель уточнює таблиці, атрибути, ключі та обмеження.
4. Атрибут стає сутністю, коли має власну ідентичність, незалежний життєвий цикл, повторне використання або зв'язки (наприклад, Автор замість текстового поля «автор» у Книзі).
