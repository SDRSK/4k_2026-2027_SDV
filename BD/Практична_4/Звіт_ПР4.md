# Практична робота №4. Перетворення ER-діаграми у реляційну схему

**Вхід:** перевірена ER-модель бібліотеки з ПР №3.  
**Вихід:** реляційна схема `Реляційна_схема.png`/`.svg`, редагований `.drawio` і виконуваний PostgreSQL DDL `schema_postgresql.sql`.

## 1. Таблиці та первинні ключі

| Таблиця | Атрибути (SQL-домени) | PK | Альтернативні ключі |
|---|---|---|---|
| `books` | `book_id UUID`, `isbn VARCHAR(13)`, `title VARCHAR(250)`, `publication_year SMALLINT`, `category VARCHAR(100)` | `book_id` | `isbn` (UNIQUE, допускає NULL) |
| `authors` | `author_id UUID`, `full_name VARCHAR(200)` | `author_id` | — |
| `book_authors` | `book_id UUID`, `author_id UUID`, `author_order SMALLINT` | (`book_id`, `author_id`) | (`book_id`, `author_order`) |
| `copies` | `copy_id UUID`, `book_id UUID`, `inventory_number VARCHAR(30)`, `condition VARCHAR(20)` | `copy_id` | `inventory_number` |
| `readers` | `reader_id UUID`, `card_number VARCHAR(30)`, `full_name VARCHAR(200)`, `email VARCHAR(254)` | `reader_id` | `card_number` |
| `librarians` | `librarian_id UUID`, `employee_number VARCHAR(30)`, `full_name VARCHAR(200)` | `librarian_id` | `employee_number` |
| `loans` | `loan_id UUID`, `copy_id UUID`, `reader_id UUID`, `librarian_id UUID`, `issued_at DATE`, `due_at DATE`, `returned_at DATE` | `loan_id` | один відкритий запис на `copy_id` (частковий UNIQUE) |

## 2. Таблиця відповідності: сутність → таблиця / зв'язок → правило

| Концептуальний елемент | Реляційна реалізація | Правило |
|---|---|---|
| Книга | `books` | Сутність → таблиця |
| Автор | `authors` | Сутність → таблиця |
| Примірник | `copies` | Сутність → таблиця |
| Читач | `readers` | Сутність → таблиця |
| Бібліотекар | `librarians` | Сутність → таблиця |
| Видача | `loans` | Сутність → таблиця |
| Книга—Автор | `book_authors` | Проміжна сутність → таблиця зі складеним PK |
| Книга 1:N Примірник | `copies.book_id` → `books.book_id` | FK на стороні N |
| Книга M:N Автор | `book_authors.book_id`, `book_authors.author_id` | Два FK і складений PK |
| Читач 1:N Видача | `loans.reader_id` → `readers.reader_id` | FK на стороні N |
| Примірник 1:N Видача | `loans.copy_id` → `copies.copy_id` | FK на стороні N |
| Бібліотекар 1:N Видача | `loans.librarian_id` → `librarians.librarian_id` | FK на стороні N |

У вихідній моделі немає зв'язків 1:1; окреме перетворення такого зв'язку не потрібне. Якби він був, можна було б використати FK із `UNIQUE` у залежній таблиці.

## 3. Зовнішні ключі та поведінка видалення

| FK | NULL? | ON DELETE | Причина |
|---|---|---|---|
| `book_authors.book_id` | NOT NULL | CASCADE | Видалення книги прибирає технічні зв'язки з авторами |
| `book_authors.author_id` | NOT NULL | CASCADE | Видалення автора прибирає лише зв'язки з книгами |
| `copies.book_id` | NOT NULL | RESTRICT | Не дозволяти видалити книгу з фізичними примірниками |
| `loans.copy_id` | NOT NULL | RESTRICT | Не втрачати історію видач примірника |
| `loans.reader_id` | NOT NULL | RESTRICT | Не втрачати історію читача |
| `loans.librarian_id` | NOT NULL | RESTRICT | Не втрачати інформацію про працівника, який оформлював видачі |

`SET NULL` не підходить для жодного з цих FK, бо всі відповідні зв'язки обов'язкові. Для майбутнього необов'язкового зв'язку `SET NULL` був би допустимим.

## 4. Обмеження цілісності за таблицями

- **books:** PK, `title NOT NULL`, непорожня назва, `isbn UNIQUE`, ISBN — 10 або 13 цифр за наявності, `publication_year BETWEEN 1450 AND 2100` за наявності.
- **authors:** PK, `full_name NOT NULL`, непорожнє ім'я.
- **book_authors:** складений PK, обидва FK NOT NULL, `author_order >= 1`, унікальний порядок для кожної книги.
- **copies:** PK, `book_id NOT NULL REFERENCES books ON DELETE RESTRICT`, `inventory_number UNIQUE NOT NULL`, `condition NOT NULL DEFAULT 'available' CHECK (...)`.
- **readers:** PK, `card_number UNIQUE NOT NULL`, `full_name NOT NULL`, email необов'язковий.
- **librarians:** PK, `employee_number UNIQUE NOT NULL`, `full_name NOT NULL`.
- **loans:** PK, три FK NOT NULL/RESTRICT, `issued_at NOT NULL DEFAULT CURRENT_DATE`, `due_at NOT NULL`, `returned_at` необов'язковий; CHECK строку й повернення; частковий `UNIQUE INDEX` на `copy_id WHERE returned_at IS NULL`.

**Важливе розмежування.** Індекс на відкриті видачі гарантує не більше однієї незавершеної видачі примірника. Він **не** перевіряє, чи перебуває примірник у стані `repair`/`lost`, і **не** забороняє перетинання історичних інтервалів дат; це можливі додаткові бізнес-правила.

## 5. Чому M:N перетворюється на таблицю

Реляційна таблиця не повинна зберігати списки зовнішніх ключів в одній комірці. Тому «книга має багатьох авторів, автор написав багато книг» перетворюється на `book_authors`, де кожний рядок — один зв'язок конкретної книги з конкретним автором. Складений PK не допускає дублювання зв'язку, а зовнішні ключі забезпечують посилальну цілісність. Атрибут `author_order` належить самому зв'язку.

## 6. Висновок

Концептуальні сутності перетворено на сім взаємопов'язаних таблиць. Для відношень 1:N зовнішній ключ розташований на стороні N, а M:N реалізовано окремою таблицею. Для ключів, допустимих значень та видалень визначено обмеження. Додатковий частковий унікальний індекс захищає від двох одночасних відкритих видач одного примірника. Реляційна схема готова до створення у PostgreSQL за допомогою файлу `schema_postgresql.sql`.

## Відповіді на питання для захисту

1. При 1:N одному батькові відповідає багато дітей; у кожного дочірнього рядка одне поле FK природно вказує на одного батька.
2. Посилальна цілісність гарантує, що FK посилається на існуючий PK/UNIQUE або є NULL, якщо це дозволено; її перевіряють обмеження `FOREIGN KEY`.
3. Створити таблицю-зв'язку з двома FK, зробити пару первинним ключем та зберігати атрибути зв'язку в цій таблиці.
4. При `RESTRICT` (або `NO ACTION`, якщо перевірка не відкладена) видалення батька з наявними дочірніми посиланнями завершиться помилкою; при `CASCADE` дочірні записи також будуть видалені.
